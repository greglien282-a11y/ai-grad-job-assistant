# 关键产品决策记录

以下记录产品设计依据，未来可用实际用户数据修正。

## D-001 · 优先应届生，不做全人群求职产品

**理由**：大学生普遍更难回忆和表达有限经历，流程痛点集中且易于设计小范围试验。  
**代价**：早期专业和行业覆盖有限。

## D-002 · “事实库”比纯文本润色更重要

**理由**：一次确认真实经历可以多次复用，降低岗位定制成本，并减少 AI 生成虚假表述的风险。  
**代价**：需要额外的数据结构和确认交互。

## D-003 · 一岗一策略优先于强行一岗一简历

**理由**：某些 JD 与用户存在真实能力差距，简单换关键词并不能弥补；系统应告知适配与缺口。  
**代价**：有些岗位不会输出看上去“变化很大”的简历。

## D-004 · 模拟面试默认短，而非无限追问

**理由**：早期对话试验中，多轮技术面试容易造成反馈冗长、缺乏停止点。  
**代价**：深度探索需由用户主动选择。

## D-005 · 不把跨平台自动投递作为 V0.3 门槛

**理由**：平台适配、授权与自动化维护成本高，易分散首个完整闭环的开发精力。  
**代价**：初期无法替代招聘网站上的全部手工操作。


## D-006 · 保留按任务难度、质量和成本选择模型的演进方向

**决策**：Pathwise 从一开始就区分 **供应商（Provider）**、**模型（Model）** 和 **任务类型（Task）**，统一接入接口、输出合同、事实校验及费用统计，避免未来更换模型时重写业务逻辑。初期只要求能够**显式配置/手动切换**供应商和模型，不在 M1-2C-2 中提前开发自动路由。

**长期设想（尚未实现）**：积累真实的、经授权的质量与成本评测数据后，研究**任务级模型路由**：例如让更低成本、经验证足够可靠的模型承担简单事实抽取，让更擅长复杂推理与交流的模型承担多轮精准追问、复杂贡献归属澄清；必要时也可以继续使用单一模型。不能预设“便宜模型一定适合抽取”或“贵模型一定追问更好”，须由相同测试集与用户反馈验证。

**为什么记录**：应届生求职产品需要兼顾实际体验和可持续成本。目标不是最低的每百万 Token 标价，而是衡量**每段完成经历的总成本、每条有效且经用户确认事实的成本、追问有效性、虚构/错误引用率、耗时及失败率**。同一模型可经不同供应商提供，须单独记录渠道、实际版本、区域、价格与数据处理条款，不能默认等价。

**后续实施前提**：
- 先完成统一 Provider 适配与基础成本/效果观测，至少能手动选择模型；积累足量对照样本后再评估是否值得做自动路由。
- 模型输出始终经过既有来源/事实校验，AI 不能自行确认事实；不能因为路由而降低真实性门槛。
- 每次调用均受预算、隐私授权、供应商区域及用户数据外发规则约束；**不允许错误后自动切换供应商、重复计费或绕过审批**。未知费用/结果保持故障关闭与显式恢复语义。
- 切换策略要可解释、可回退，并衡量整体用户收益及工程维护成本；不因概念先进而引入多 Agent 或复杂调度。

**当前状态**：设计方向已记录，**未实现**；不构成任何模型/供应商选择、真实 API 调用、费用开支或自动路由开发授权。现阶段 M1-2C-2 仍按零费用评测设计与后续单独审批推进。
