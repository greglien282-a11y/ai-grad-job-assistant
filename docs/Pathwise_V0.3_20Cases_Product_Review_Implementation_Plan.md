## 1. 产品目标及不可突破的底线

**产品目标：** 用户像聊天一样描述经历，Pathwise 在后台提取、去重、维护**待确认**事实；只做必要且高价值的追问；最后集中提供用户审核，形成可复用、真实的经历资料，为未来“一岗一简历”提供基础。

**不可突破：**

1. **自动维护 ≠ 自动确认。** 模型提取或用户新增的事实原则上进入 `pending`；只有用户明确审核才能进入 `user_confirmed`。已有确认事实被实质修改后应重新进入待确认状态；不能绕过历史状态机、来源校验或证据状态。
2. 保留来源、引用位置、版本、变更历史、拒绝事实及用户的否定/纠正边界。模型不能把团队成绩写成个人成绩、把计划写成完成、把未知指标写成已测量。
3. 语义关联、自动纠错、自然语言停止必须具备**不确定时不臆断**的处理方式，不得产生隐式重复 POST、换幂等键、自动恢复推理、越过轮数/停止门禁。
4. **当前业务限制保持：** 最多六轮独立挖掘、现有重试/幂等与付费门禁不变；任何重新设计均需单独审查。
5. 仅允许受控的离线合成测试；**不得**开启真实供应商调用、付费额度、生产库、真实用户数据上传或生产部署；需要这些行为时先单独取得明确授权。

## 2. 20/20 案例产品判定与建议改动

| 案例 | 产品侧确认的处理原则 | 建议实现/评测侧关注 |
|---|---|---|
| GQ01 课设与后补具体工作 | 用户后续给出明确个人工作，直接增补待确认事实；不为表面冲突反复澄清 | 来源跨轮关联；不自动确认、不重造个人职责 |
| GQ02 团队分工不清 | 项目背景可保留；个人分工不清时问一次本人具体做过什么，允许记不清 | 背景与个人贡献分离 |
| GQ03 基础数据整理 | “我整理了27条缺失记录”应可成为待确认事实；进一步问处理方法 | 当前 `atomic()` 不认“整理”，保留差异、单独评估校验改进 |
| GQ04 手工测试 | 优先追问测试方法、场景、发现，而不是证明材料 | 提问收益优先于索证 |
| GQ05 “我们”与“我” | 团队实现只作背景，个人动作须从明确陈述提取 | 防止团队成果冒充个人 |
| GQ06 无量化指标 | 自动记下“未测速度/无访问量”；问具体改动而非要求猜百分比 | 数值编造与反复追问为严重风险 |
| GQ07 记不清规模 | 接受未知与不愿猜；转向记得的工作，不反复追问规模 | 未知边界、允许停止 |
| GQ08 未执行计划 | 区分计划、进行中、已完成；新进展主动补充时更新待确认事实 | 禁止把计划当成果；需要进度状态方案 |
| GQ09 明确否认 | “没部署过”作为限制条件保存，追问其他个人工作，不把否定写成亮点 | 否定不能丢失、不能重新复活 |
| GQ10 只有课程学习 | 区分知识储备、练习、项目；可以记录学习，但绝不伪造完成的应用 | 技能背景与项目证据区分 |
| GQ11 多项原子动作 | 自动拆分三项待确认事实；只择重点追问，最终集中审核 | 多事实来源切片；防止“全栈”虚构 |
| GQ12 明确纠正 | 后一句明确纠错应使旧个人贡献失效、新事实待确认；不重复问“是否确认纠错” | 不复活旧版本；保留变更历史 |
| GQ13 拒答/跳过 | 自动尊重“跳过此题”；跳过当前问题不等于结束整个会话 | 区分问题跳过、当前话题结束、会话结束；谨慎处理 `stop` 语义 |
| GQ14 两题只答一题 | 尽量自动语义关联明确回答；未回答问题保持未知，不机械提醒或强绑 | 现有显式 ID 关联是可靠底线；不确定时不得臆断 |
| GQ15 用户主动停止 | 请求停止应由业务门禁执行，不进入模型评分/派发；用户仍可审核旧事实 | **business_gate/no-dispatch**；自然语言停止需在供应商调用前处理，测试 0 派发 |
| GQ16 六轮上限 | 合法第六轮先保存新增待确认事实，再停止追问；不宣称经历已完整 | 后端轮数与完成事务回归；不要变更六轮上限 |
| GQ17 经历很少 | 两轮没有新增事实时依规则停止，不编造项目；可自主探索其他素材 | **business_gate/no-dispatch**；不把“无项目”当用户失败 |
| GQ18 无证明材料 | 保留已确认测试事实，不强索截图/数据，不臆造证明；允许以后主动补充 | 已确认事实与材料证据分离；尊重拒绝 |
| GQ19 普通工作价值 | 真实的名单更新值得记录；问具体流程，不预设一定做过核对 | 不夸大普通岗位，不必硬造 KPI |
| GQ20 Emoji/Unicode | 原话“我制作了🧪原型图”原样保存，来源区间准确；问题不预设部署 | Python Unicode code point 与浏览器 JS UTF-16 索引转换的端到端回归 |

**备注：** GQ15/GQ17 属于业务门禁案例，不应被纳入模型生成质量分母。GQ13 的“停止继续生成本轮追问”与业务“会话已停止”必须单独审查，不能仅改口头定义。

## 3. 当前已具备的功能（仅以已检查代码为准）

- **事实真实性基础：** `apps/api/app/facts.py` 已有 `pending / user_confirmed / evidence_supported / rejected` 状态、用户编辑重回 `pending`、单独确认操作、版本冲突检查、变更历史及来源快照；`eligible_facts()` 仅使用确认/证据支持的事实。
- **后端安全边界：** `apps/api/app/mining.py` 管理幂等、恢复、问题关联、六轮上限与停止状态；`complete()` 不会把模型候选自动确认为用户事实；`mining_api.py` 有显式 `mining-stop`、`skip/correct/hide/delete` 问题接口。
- **当前问题关联依赖用户操作：** `apps/web/src/features/discovery/QuestionCard.tsx` 显示勾选框或“回答这题”按钮；后端 `answered_question_ids` 与问题版本是显式关联，不是自动语义识别。
- **已有集中审查入口但流程可优化：** `apps/web/src/features/discovery/FactReview.tsx` 提供事实列表和逐条审核；不等于已实现自动合并纠正、批量确认或低操作量体验。
- **当前词法校验严格：** `apps/api/app/mining_validation.py::atomic()` 仅认可现有动作词表，GQ03 的“整理”不匹配；`sentence_spans()` 使用 Python Unicode code point。
- **质量评测工具：** `docs/evaluation/quality-v1/` 保留 20 个虚构 DRAFT 场景、6 维 0–4/N/A Rubric；没有人类语义模型评分、独立真实模型输出质量或认证的审核人身份。

## 4. 已识别的实现缺口与优先级

| 优先级 | 功能缺口 | 为什么不能只改提示词 |
|---|---|---|
| P0 | 用户自然补充/明确纠错 → 待确认事实的版本化更新 | 涉及同一事实识别、旧状态失效、版本并发、拒绝事实不复活、审计历史；必须有后端一致性校验 |
| P0 | 追问/回答的低操作量体验 | 现有显式问题 ID 关联既安全又繁琐；自动关联需要置信边界、歧义回退和端到端测试 |
| P0 | 跳过某题与停止全轮/全会话的语义分离 | 当前 `mining.py::complete()` 中模型 `stop=true` 会设 `mining_status='stopped'`；不能直接把自然语言“跳过”翻译成同一个永久状态 |
| P0 | GQ15 停止请求业务门禁 | 当前有显式停止 API/界面操作；若支持自然语言停止，必须先于模型派发、具备授权/归属检查、无隐式 Provider 调用 |
| P1 | 审核工作台操作量下降 | UI 可改为集中审查和按需展开，但仍不能把 pending 偷偷改成 confirmed |
| P1 | 课程/项目背景、计划/完成、否定/未知的结构化区分 | 当前已有事实和 memory_state 字段，不代表已经支持所需的完整语义结构；如需 schema 变更先设计 |
| P1 | 评测用户操作成本与追问收益 | 现有六维 Rubric 主要判断输出质量，没有可复现的交互成本证据 |
| P2 | Unicode 端到端与 GQ03 词法差异 | 必须有真实正反例，不能简单放宽以追求 Oracle 满分 |

**注意：** GQ01 的“后补具体工作”与 GQ12 的“明确撤回旧陈述”不同；不得把所有后续句子无条件覆盖前句。自动更新只应作用于可定位的待确认事实；任何修改过的已确认事实应依现有规则重新待确认。

## 5. 推荐开发顺序（每阶段独立 Draft PR，独立复审）

### 阶段 A — 固化产品决策与设计（文档和离线测试先行）

- 在仓库新增产品侧决策说明及 20 案例映射，标注“用户确认的产品规则、非人工模型输出评分”。
- 为「用户普通补充 / 明确纠错 / 否定 / 计划进度 / 问题跳过 / 当前话题结束 / 停止整个挖掘」定义清晰的状态与操作边界；先提供序列图和迁移/非迁移选项。
- 列出每类情景的预期请求次数、可见 UI、数据变化和审计事件。明确 GQ13 与 GQ15 的差异。
- **不改** PR #30 冻结的 dataset/rubric/report/hash、现有生产状态机与数据库结构。
- 交付物：产品决策文档、状态映射、回归测试计划；独立 Draft PR，等待人工审查。

### 阶段 B — 后端待确认事实维护（合成、可追溯、安全）

- 在用户显式提交新的自然语言内容后，识别新增动作、对旧陈述的明确否定/纠正、计划进度变化，落到可审计的 **pending 候选** 与变更关系；不绕过 `change_fact` 已有状态约束。
- 同一事实重复表达不产生重复候选；拒绝事实、已撤回事实不能因新一轮挖掘重新复活。
- 清楚区分“用户陈述的来源”与“模型解释/摘要”。有歧义时保守处理，不作静默确认或删除。
- 回归：GQ01/GQ03/GQ05/GQ08/GQ09/GQ11/GQ12/GQ18、事实并发冲突、编辑后确认状态、版本/来源历史、幂等与重复提交。
- 若需要数据库迁移，先单独提交 schema/合同审查，未经批准不触及生产数据库。

### 阶段 C — 减少重复提问与用户操作

- 引入“显式 ID 关联优先、能确定才自动关联、不确定时保留未回答”的语义关联方案。
- 支持用户自然表达“跳过这题”，不要求先勾选/点击跳过；只改变对应问题状态，不自动停止整个会话。
- 自然语言“先停在这里”的判定必须在任何 Provider 派发前可靠转成已授权业务停止；不确定时不得擅自触发新请求。继续挖掘必须经用户明确授权和既有合同许可。
- 问题数量始终遵守上限；优先补具体动作、贡献、场景，避免索证、重复逼问数字或已明确拒绝的信息。
- 回归：GQ02/GQ04/GQ06/GQ07/GQ10/GQ13/GQ14/GQ15/GQ16/GQ17/GQ19；每个动作的 `POST` 计数与停机后无派发。

### 阶段 D — 用户界面与集中审核体验

- 对话页优先“自然输入—连续补充”；隐藏不必要的技术操作项，但保留高级控制入口、清楚的状态反馈和无障碍交互。
- 审核页一次展示该段经历待确认事实，允许用户快速确认/编辑/拒绝；编辑过的事实重新待确认，不做默认批量同意。
- 减少每轮打断式的确认；任何高风险动作（删除、越权共享、生产派发等）仍须显式授权。
- 评测实际点击/操作次数、冗余追问、完成时间，而不是单纯以页面更少为成功。
- 与**单独的 React 时序不稳定排查 PR**隔离，禁止借 UX 改版掩盖 `InteractionFlow.test.tsx:93` 已知竞态。

### 阶段 E — 质量评测新版本（在功能实现和独立审核之后）

- 在新版本/新摘要中记录用户批准的产品行为目标；**不要就地重写**已冻结的 `quality-v1` 样例和对应报告而破坏可复现性。
- 保留六维模型语义评分，新增独立的**交互成本/有效追问**指标。建议：每段经历用户显式操作数、每条有效待确认事实所需追问数、重复/被拒绝话题追问率、无依据追问率、因答题关联歧义触发确认率、任务完成耗时（真实测量方可报告）。
- 为自动处理纠错、否定、跳过、停止设置严格的安全与真实性负例；严重事实编造独立阻断，不能与良好 UX 分数抵消。
- GQ15/GQ17 继续作为 business_gate，不纳入模型指标分母。GQ16 合法第六轮仍可产生事实后停止；GQ13 跳过与停止语义必须在新合同中讲清。
- **产品决策不是模型质量的人工 gold。** 如需人类模型评分，必须逐条审核真实待评输出、记录证据、评分理由/审核者状态及必要时的第二人复核。20 例目前已公开讨论，不能宣称是秘密盲测集。
- 真实大模型的最小合成实验、价格/预算及供应商审批另开流程，当前不授权。

## 6. 必须保留的工程验收指标

**事实与安全硬约束（必须为 100%）：** 无自动确认；无虚构来源；否定/旧版本不复活；已拒绝事实不得绕过；不复制团队贡献；超限/停止后不产生新 Provider 调用；每次用户提交最多一条合法幂等操作；Unicode 引用定位正确；无真实凭据/费用/生产库访问。

**体验改进指标（仅在合成可测样本或自愿用户测试中报告真实基线和改善）：**

- 每段经历必需点击数（与旧流程同任务对照）。
- 完成事实审核的点击/操作数；哪些仍必须让用户自主决策。
- 有效新增事实 / 追问轮数，冗余问题 / 总问题，忽略拒答 / 总拒答场景。
- 自然回答正确关联率、歧义案例的安全回退率。
- 对于无指标、无材料、经历少的场景，是否仍能真实结束而不被迫“补全”。

不要预先设定“提升百分比”，没有测量不能声称收益。代码侧正反例要同时通过；任何项目经历文本的质量高低仍以可核对来源为边界。
