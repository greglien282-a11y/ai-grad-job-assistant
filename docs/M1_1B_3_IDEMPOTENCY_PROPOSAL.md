# M1-1B-3 幂等修复提案（待批准，尚未实施）

## 已复现的阻断问题

真实 React → FastAPI → PostgreSQL，提交到真实服务后丢弃响应，不伪造成功。

- 创建返回 201、数据库已有 1 个会话，但浏览器没有凭证，不能读取、导出或删除该会话。
- 新增事实返回 201、数据库已有 1 条事实，界面保留输入。手动重试后数据库出现 2 条事实。
- 两项验收测试保留原始成功条件，正常失败；不得用 skip、预期失败、放宽断言或 continue-on-error 隐藏。

## 建议的最小合同扩展

保留现有分步新增接口与整数版本检查，不增加原子业务接口。仅对创建会话、新增对话回合、新增事实的 POST 引入可选 `Idempotency-Key`。旧客户端行为兼容。

1. 新增一张操作表：作用域（创建会话全局 / 已鉴权会话）、操作种类、键摘要、规范请求摘要、结果记录 ID、创建时间。唯一约束控制并发；与业务写入同一事务提交。键和正文不同则 409。授权先于重放；已删除会话不能借旧键复活。保留策略必须覆盖客户端重试窗口，不能默默过期后重复执行。
2. 创建会话首次请求前，浏览器生成 32 字节加密随机临时凭证及独立操作键。幂等创建使用 `Authorization: Bearer` 传输这枚临时凭证；服务端校验格式后将其摘要作为该会话现有授权摘要。丢失响应时，同一凭证、键及正文重试即可获取同一会话；服务端无须保存明文凭证，也不增加加密密钥。无幂等键的旧创建路径继续由服务端生成凭证。凭证不进入 URL、操作表正文、日志或导出。创建请求的错误日志仍必须抹去 Authorization。
3. 新增回合和事实分别使用稳定操作键；同一已授权会话中的重试返回原记录，不重复插入来源、事实和历史。现有两次 POST 的部分成功仍可逐步恢复，无须改成新原子接口。
4. 前端创建未完成时在 sessionStorage 临时保留操作键及凭证，不保存经历正文。成功后只保留现有会话 ID/凭证结构。新增事实的两枚键留在组件内存，确认结果前不换键；刷新后先读取服务器，不能自动补发未知结果。重放内容不同应展示明确冲突，允许用户决定新操作。

## 影响与待审事项

- 后端：三个 POST、一个 SQLAlchemy 模型、一版 Alembic 迁移；不改 PATCH 的 version/409 合同。
- 前端：创建/新增重试的操作状态；扩展开发期暂存结构，仅用于尚未拿到创建响应的短暂窗口。
- 安全：客户端提供的凭证必须来自 Web Crypto，长度与编码由服务端严格限制；创建重放需同时证明持有相同凭证。任意客户端都可以创建匿名会话，因此仍需后续限流/正式身份机制。
- 测试：真并发相同键、不同正文、错凭证/跨会话、删除后重放，以及上述两个浏览器阻断用例；对话回合响应丢失也需要新增回归。
- 需要审查删除时如何处理全局创建操作墓碑，及服务端操作保留期限。推荐删除业务数据并保留无内容/无凭证的键墓碑，旧键返回 410；现有 409 文案需区分版本冲突与幂等正文冲突。
