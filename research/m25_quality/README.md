# M2.5 offline quality diagnostics

This is an executable **offline research tool**, not a Provider, official fact writer, calibrated semantic evaluator, or production quality gate. It imports only the Python standard library. All 60 inputs are public synthetic examples created for this repository. They contain no real applicant identity, contact information, credential, or personal resume. Every explanatory label is `draft_unreviewed` and every `human_review` is `null`.

## Run

From the repository root with Python 3.12 and pytest available:

```powershell
python -m pytest research/m25_quality/test_quality.py -q
python research/m25_quality/quality.py verify
python research/m25_quality/quality.py baseline --output baseline-new.json
python research/m25_quality/quality.py evaluate --input baseline-new.json --output diagnostics-new.json
python research/m25_quality/quality.py evaluate --input research/m25_quality/fixtures/deliberate-negative-candidates.json --output negatives-new.json
```

The last command intentionally returns **1**, after writing five detected failures and two uncertain blind spots. Exit **0** means a valid diagnostic execution with no supplied hard failure; it does **not** mean model quality passed. Exit **2** means a document/contract error. Existing output files are refused, preserving prior evidence. Use a new filename for each run. No retry, network, credentials, account, database, model inference, or paid call is used.

The committed `reports/*.generated.json` files are reproducible generated diagnostics. The baseline file is generated by the lexical baseline and then checked by this tool solely to demonstrate protocol/CLI operation. **This self-consistency run cannot be used to claim model quality.** External offline candidates use `m25-candidate-batch-v1` with a `cases` object keyed by frozen case ID; each value has the same versioned candidate packet parsed by TypeScript. Unprovided cases remain `supplied: null`, not silently substituted with successful baseline results. Unknown case IDs are rejected.

## What is frozen

`cases-v1.json` contains 60 genuinely different scenarios: course-only/no project/no metrics, team responsibility, planned/ongoing/negative/unknown claims, source overstatement, required/bonus/conflicting/vague JD requirements, role transfer/order, synonyms/abbreviations/English, Unicode/combining marks/ZWJ/CRLF, missing evidence, numeric variants, rejected-history risks, unrelated contributions, manual self-declarations, conditional claims, education, DOCX-table/PDF-column snapshots, conflicting sources/states, JD negation/alternatives/seniority, explicit self-assessed gaps, and separately sourced plan/later action.

`cases-v1.manifest.json` freezes each case and the complete corpus using SHA-256 over UTF-8 JSON with sorted keys, compact separators, and literal Unicode. Corpus SHA:

```text
78715182dbe9a6ee0fab08fbe740993d8ee190aaabe2eb5bbdfa80f8d66f2192
```

This is a **content freeze**, not a gold-label or product-policy approval. Do not edit v1 observations to make a candidate pass. A correction requires a new corpus version and manifest, a documented dispute, and independent review. Keep the original case, raw failing candidate, and original report. A frozen file is not necessarily a correct reference answer.

## Candidate binding and seven dimensions

The strict `local-suggestion-candidates-v1` packet binds a role to full source and JD snapshots. A suggestion references an existing complete paragraph and complete JD requirement, including exact IDs, kind, original quote, and Unicode code-point half-open offsets. The snapshot is a **local review snapshot**, not an original file byte offset, authenticated User Turn, FactV3, or audit receipt. Manual statements have `user_manual_statement` kind; they do not become imported evidence.

All objects reject extra/missing fields and unknown versions. Duplicate JSON keys (including escaped aliases), IDs, source/JD candidate pairs, invalid Unicode, unsafe control/bidi characters, suspected credentials, invalid ranges, forged source kinds, cross-source references, and stale corpus/role snapshots are rejected. Python and TypeScript share `contract-fixtures.json`: five valid packets (normal, Unicode, manual, CRLF, mathematical-integer JSON values) and twenty-one negative packets. JSON numbers such as `1`, `1.0`, and `1e0` denote the same mathematical integer; both parsers accept them in integer fields but reject booleans, fractions, and nonfinite numbers. Python converts indexes only internally after validation for slicing, without rewriting the original packet. Original complete paragraphs may be reordered or overlap because the existing local workbench allows such excerpt metadata; this tool does not invent a stricter source contract.

The Python CLI accepts a **batch document** up to 2 MiB with nesting capped at 24; each parsed packet has its own compact-JSON 512 KiB budget. The browser accepts a **single raw packet** up to 512 KiB and uses its existing JSON-depth guard (32). These are different container/resource boundaries, not identical raw-JSON byte acceptance rules. Shared fixtures check the parsed packet's meaning and source graph; they do not prove exhaustive byte-level parser equivalence.

Each case reports findings in seven separate dimensions:

- `jd_requirements`: exact quote binding is observable; extraction completeness/meaning requires review.
- `association`: finite literal intersections are observations, not semantic matches or proficiency.
- `source_fidelity`: exact source graph/quote preservation; not fact truth or original-file extraction correctness.
- `fabrication_risk`: known new numeric tokens/protected vocabulary are flagged. All changed-text entailment remains uncertain, even when no finite rule fires.
- `state_preservation`: original text is retained; selected Chinese plan/team/negation/uncertainty marker loss is a known-risk detector.
- `usefulness_explanation`: human judgment remains required.
- `clarification`: changes, explicit new claims, and restricted context remain unproven. A confirmation button is not proof.

Every report preserves per-case rule details, exact quoted source, separate pass/fail/uncertain finding counts, and independent hard-failure records. There is **no averaged quality score**. `accuracy` and `fact_error_rate` are always null. A hard graph check can pass while the overall case remains uncertain. The evaluator cannot automatically produce a semantic success verdict.

## Lexical baseline and preserved failures

The baseline uses the existing M2 vocabulary and ASCII word-boundary behavior for Python/PyTorch/OpenCV, plus exact Chinese term occurrences. It recommends only exact source originals and ranks edges deterministically. It is explicitly the **lexical core**, not the UI's full source admission, risk, gap, conflict, deduplication, or print policy. The UI must independently enforce those existing gates.

The baseline is reproducible and explainable but misses synonymous expressions/abbreviations, can match a word in a negated JD requirement, and cannot prove scope, completion, education, responsibility, relevance, or source truth. An original overstatement remains an unverified user assertion; retaining it is not a factual endorsement. No false matching percentage is output.

`fixtures/deliberate-negative-candidates.json` preserves seven deliberately unsafe rewrites. Five trigger finite diagnostics (invented numbers or removal of Chinese qualifiers); two English plan/team responsibility changes remain **uncertain**, demonstrating an important blind spot. Do not turn those two into success or delete them. Digital spelling changes, synonyms, a new Turn/key, or replacing IDs do not establish R03 independence. This evaluator has no authenticated complete session history and cannot decide transaction-level historical admission.

## Human review, disputes, and later freezing

Create a separate `m25-human-review-claim-v1` JSON sidecar containing:

```json
{
  "contract": "m25-human-review-claim-v1",
  "corpus_sha256": "78715182dbe9a6ee0fab08fbe740993d8ee190aaabe2eb5bbdfa80f8d66f2192",
  "reviewer_id": "REPLACE-WITH-ACTUAL-REVIEWER",
  "provenance": "REPLACE-WITH-REVIEW-METHOD-AND-RECORD",
  "entries": [{
    "case_id": "M25-001",
    "decision": "uncertain",
    "rationale": "REPLACE-WITH-INDEPENDENT-JUDGMENT",
    "evidence_ref": "REPLACE-WITH-REVIEW-RECORD"
  }]
}
```

This is a template, **not an existing review**. `decision` is `agree`, `dispute`, or `uncertain`. Run `quality.py review --input review-file.json` to check its structure and corpus binding. The result always retains `identity_verified=false` and `gold_authorized=false`: a local string claiming a reviewer identity cannot prove independence, authority, or a natural person's review.

For each disagreement, retain the original draft label and candidate, add the review rationale/evidence reference, and leave the case disputed until an authorized human resolves it. A future separately approved release may reference independent reviews and a new immutable manifest; this tool cannot approve that release or upgrade the current labels itself. Human review of wording also does not verify real-world facts.

G4, T2/T3, shared CO key-domain, R03, D4/D5, remaining D6, and D8 blocks remain. No formal typed writer, CO3, Fact classification, production permission, migration, or Provider contract is changed here.
